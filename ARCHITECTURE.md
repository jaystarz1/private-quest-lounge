# Architecture — private-quest-lounge

## Components

```
Browser (Quest Browser / desktop Chrome)
   │  HTTPS + WSS
   ▼
reticulum (Elixir/Phoenix, :4000) ── postgres 14
   │  rooms, presence (Phoenix Channels), auth (magic links), permissions
   │  proxies the hubs client + admin in dev
   ▼
dialog (Node + mediasoup SFU, :4443 + UDP 40000-40050)
      WebRTC voice; TURN (coturn) needed in production for strict NATs

hubs client (webpack dev server :8080 in dev; static files in prod)
      Three.js + A-Frame + bitECS WebXR client — all our UX changes live here
```

`postgrest` and `hubs-admin` (:8989) exist for the operator only; participants
never touch them. Spoke (scene editor) is behind the `extras` compose profile
and unused — the lounge scene is generated, not authored in Spoke.

## Room access model

- A room's URL contains its unguessable 7-char `hub_sid` (e.g.
  `https://host/XDmNmuE/slug`). That URL **is** the invite; there is no room
  directory, search, or promotion (rooms default to unlisted, and the client
  surfaces no browsing UI).
- `features|disable_room_creation` — only admin accounts create rooms.
- `features|disable_sign_up` — no new accounts; guests join anonymously with a
  display name.
- `room_size` is forced to 2 (`features|default_room_size` and
  `features|max_room_size`). Capacity is enforced at entry via presence
  slot-counting (`canEnterRoom`); a third visitor stays in the lobby with a
  "room is full" screen. The room creator bypasses the check (host can always
  return). This is entry-flow enforcement, not a socket-level wall — the
  unguessable URL is the primary access control.
- Member permissions are restrictive: voice and text chat only. No media
  spawning, drawing, camera, emoji or fly, so nothing can be uploaded or
  spawned even via the protocol.
- Bad invite links render the standard "bad Room ID" screen.

## Scene (client fork)

`getSceneUrlForHub` in `src/hub.js` returns the bundled `lounge.glb` for every
hub unless the operator explicitly assigns a scene in reticulum. The GLB is
generated by `lounge-assets/generate-lounge.mjs`: ~63 meshes, 2.1k triangles,
139 KB, flat-colour materials, no textures. Behaviour comes from
`MOZ_hubs_components` node extensions:

- `nav-mesh` (invisible merged plane; teleport locomotion honours it)
- 2 `spawn-point`s facing into the room (avatars face waypoint +z)
- 4 seat `waypoint`s (`canBeOccupied`, `canBeClicked`, `willDisableMotion`),
  one per couch cushion; clicking a cushion seats you, moving/teleporting
  releases the seat
- `ambient-light` + 2 warm `point-light`s (lamps) + a faint moon light;
  no shadow casters
- `RainFX` node reserved on the window pane for a future cheap rain shader

## Avatars (client fork)

Two fixed MetaPerson half-body avatars (head, torso, arms, and hands; no legs)
live in `src/assets/models/lounge-avatars/`, generated from
`lounge-assets/metaperson-*/hubsify.py`. They retain the arm chains and keep
the named hand effectors directly under `Spine`, matching the chest-relative
transforms that the stock `ik-controller` writes. They copy the upstream
`DefaultAvatar` proportions and a Hubs-compatible head and hand naming scheme.
`player-info` hides the whole body in first person (third-person-only camera
layer). A `Mouth` node carries `scale-audio-feedback` so the mouth pulses while
speaking. The picker offers Jay and Tracy only; there is no avatar browsing or
upload. Because avatars are addressed by URL through the standard
`player-info` protocol, replacing a preset remains an asset-only change.

## Removed / disabled upstream features

| Feature | How |
|---|---|
| Public room browsing/discovery | No UI; rooms unlisted by default |
| Room creation by participants | Server: `disable_room_creation` (admin-only) |
| Account sign-up | Server: `disable_sign_up` |
| Media upload/spawn, pen, camera, emoji, fly | Server: restrictive member permissions; client: Place/Share/Reaction/Objects UI removed |
| Avatar browsing/upload | Client: picker replaced by fixed six; media-browser route unused |
| Scene browsing/Spoke | Compose profile `extras` (not started); no client entry point |
| Favorites, streamer mode, in-room Create Room | Client: More-menu items removed |

Operator/admin access (`https://host:8989`, reticulum console) is intentionally
untouched and documented in README step 6.

## Configuration

Environment-based, nothing hard-coded: hostnames and service wiring live in
`docker-compose.yml` (dev) / Community Edition values (prod); server policy in
`priv/repo/lounge_config.exs` (idempotent, re-runnable); no analytics or
third-party calls added anywhere.

## Persistence

Postgres holds accounts, hubs and app config (named volume `pgdata`).
Reticulum file storage volume exists but is effectively unused since uploads
are disabled. Avatars and the scene ship inside the client bundle.
